1Архітектура

ReadMania — вебзастосунок із трьох частин, кожна з яких працює у власному Docker-контейнері. Зовні доступний лише вебсервер; бекенд і база даних — тільки у внутрішній мережі.

Профілі бекенду
  • local — для розробки й демонстрації: листи пишуться в журнал, у базу додаються тестові дані.
  • prod — для роботи: листи надсилаються через SMTP, cookie сеансу лише через HTTPS, Swagger вимкнено, тестові дані не додаються.

3Склад поставки

Замовник отримує:

  • вихідний код у репозиторії: каталоги backend/ і frontend/, у кожному Dockerfile; у корені — docker-compose.yml;
  • шаблони конфігурації: backend/src/main/resources/application-example.yml і перелік змінних середовища з розділу 5.2;
  • міграції бази даних у backend/src/main/resources/db/migration: схема створюється автоматично під час першого запуску бекенду;
  • документацію в каталозі docs/: опис API (API.md, openapi.json), ER-діаграму (ERD.md), опис розсилки листів, ці настанови;
  • початковий дамп бази зі структурою й довідниками — за домовленістю, у форматі pg_dump -Fc.

Наповнення каталогу після передачі виконує Менеджер через вебпанель: імпорт із CSV або додавання вручну. SQL для цього не потрібен.

4Локальний запуск

Для перевірки, навчання чи демонстрації застосунок запускається однією командою на комп’ютері з Docker Desktop.

# у корені репозиторію
docker compose up -d --build
# або те саме через скрипт
./run-docker.sh up
АдресаЩо відкриває

http://localhost:8080/swagger-ui.htmlопис API (лише профіль local)
http://localhost:8080/actuator/healthстан бекенду

Локальний профіль створює тестового Менеджера manager@readmania.ua (пароль у docker-compose.yml) і тестові дані каталогу. Зупинити: docker compose down; видалити разом із даними: docker compose down -v.

Не для робочого сервера

docker-compose.yml містить відкриті тестові паролі, профіль local і відкритий порт бази даних. Для роботи використовуйте налаштування з розділу 5.

5Розгортання в хмарі

Нижче — порядок для віртуальної машини з Docker. Для PaaS див. 5.6.

Підготовка сервера

  1. Створіть ВМ з Ubuntu 24.04 LTS (2 vCPU, 2 ГБ RAM, 20 ГБ SSD).
  2. Направте доменне ім’я (запис A) на IP-адресу сервера.
  3. Відкрийте у брандмауері лише порти 22 (SSH), 80 і 443.
  4. Установіть Docker за офіційною інструкцією й увімкніть автозапуск: sudo systemctl enable docker.
  5. Скопіюйте на сервер код застосунку, наприклад у /opt/readmania.

Змінні середовища

Секрети зберігайте у файлі /opt/readmania/.env з правами 600. Ніколи не додавайте цей файл до репозиторію.

Запуск

Створіть поруч із docker-compose.yml файл docker-compose.prod.yml, який перевизначає налаштування для роботи:

services:
  db:
    environment:
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
    ports: !reset []              # база недоступна ззовні
    restart: unless-stopped
  backend:
    environment:
      SPRING_PROFILES_ACTIVE: prod
      DB_PASSWORD: ${DB_PASSWORD}
      APP_INITIAL_MANAGER_EMAIL: ${APP_INITIAL_MANAGER_EMAIL}
      APP_INITIAL_MANAGER_PASSWORD: ${APP_INITIAL_MANAGER_PASSWORD}
      SPRING_MAIL_HOST: ${SPRING_MAIL_HOST}
      SPRING_MAIL_PORT: ${SPRING_MAIL_PORT}
      SPRING_MAIL_USERNAME: ${SPRING_MAIL_USERNAME}
      SPRING_MAIL_PASSWORD: ${SPRING_MAIL_PASSWORD}
      SPRING_MAIL_PROPERTIES_MAIL_SMTP_AUTH: "true"
      SPRING_MAIL_PROPERTIES_MAIL_SMTP_STARTTLS_ENABLE: "true"
    ports: !reset []              # бекенд лише у внутрішній мережі
    restart: unless-stopped
  frontend:
    ports: !override
      - "127.0.0.1:8081:80"       # доступ лише для проксі з HTTPS
    restart: unless-stopped
cd /opt/readmania
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
docker compose ps                 # усі три служби мають бути healthy

HTTPS

Найпростіше — Caddy: він сам отримує й поновлює сертифікат Let’s Encrypt і за замовчуванням використовує лише TLS 1.2 і 1.3.

# /etc/caddy/Caddyfile
shop.example.com {
    reverse_proxy 127.0.0.1:8081
}
sudo apt install caddy
sudo systemctl reload caddy

Проксі має передавати заголовки X-Forwarded-Proto і X-Forwarded-For (Caddy робить це сам): бекенд налаштований довіряти їм, щоб правильно працювала захищена cookie сеансу.

Якщо використовуєте nginx: ssl_protocols TLSv1.2 TLSv1.3;, сертифікат — через certbot --nginx.

Перший запуск

  1. Під час старту бекенд сам створює схему БД (Flyway) і першого Менеджера зі змінних APP_INITIAL_MANAGER_*.
  2. Відкрийте сайт, увійдіть як Менеджер, змініть пароль у профілі.
  3. Видаліть APP_INITIAL_MANAGER_PASSWORD із .env і перезапустіть бекенд.
  4. Перевірте лист: наприклад, запросіть відновлення пароля для тестового email.
  5. Передайте Менеджеру доступ і Настанову менеджера: далі каталог і заклади наповнюються через вебпанель.
  6. Налаштуйте резервне копіювання (розділ 7) і моніторинг (розділ 9).

Варіант PaaS

На платформах на кшталт Render застосунок розгортається з репозиторію як два вебсервіси за наявними Dockerfile плюс керована PostgreSQL 17.

  • Змінні середовища з розділу 5.2 задаються в панелі платформи; DB_URL — адреса керованої БД у форматі jdbc:postgresql://….
  • HTTPS і сертифікати платформа надає сама.
  • У frontend/nginx.conf замініть адресу http://backend:8080 на внутрішню адресу сервісу бекенду.
  • Резервні копії керованої БД увімкніть у панелі з терміном зберігання 14 днів.

6Електронна пошта

У профілі prod листи надсилаються через SMTP-сервер зі змінних SPRING_MAIL_*; адреса відправника — SPRING_MAIL_USERNAME. Надсилання асинхронне: збій пошти не зупиняє оформлення замовлення, а потрапляє в журнал бекенду.

Адреса менеджерів

Адреса managers@readmania.ua поки задана в коді. Створіть таку скриньку (або переадресацію) на домені магазину чи замовте розробникам зміну адреси.

Щоб листи не потрапляли в спам, налаштуйте для домену відправника записи SPF, DKIM і DMARC за інструкцією вашого поштового провайдера.

7Резервне копіювання й відновлення

Усі дані магазину, включно з обкладинками, зберігаються в PostgreSQL, тож достатньо копіювати базу даних. Резервне копіювання налаштовується на сервері (у застосунок воно не вбудоване).

Щоденна копія

Скрипт /opt/readmania/backup.sh:

#!/usr/bin/env bash
set -euo pipefail
DIR=/var/backups/readmania
mkdir -p "$DIR"
FILE="$DIR/readmania-$(date +%F).dump"
# стиснений дамп у форматі custom: швидке й вибіркове відновлення
docker exec readmania-db pg_dump -U readmania -d readmania -Fc > "$FILE"
# копія в окреме сховище (S3-сумісне, інший регіон)
rclone copy "$FILE" offsite:readmania-backups/
# зберігаємо 14 днів локально й у сховищі
find "$DIR" -name 'readmania-*.dump' -mtime +14 -delete
rclone delete --min-age 14d offsite:readmania-backups/
chmod 700 /opt/readmania/backup.sh
sudo crontab -e
# щодня о 03:00
0 3 * * * /opt/readmania/backup.sh >> /var/log/readmania-backup.log 2>&1

Так виконуються вимоги ТЗ: копія щодня, зберігання 14 днів в окремому сховищі, втрата даних не більше 24 годин. Раз на місяць перевіряйте, що копії з’являються й відновлюються (наприклад, на тестовій ВМ).

Відновлення

  1. Зупиніть бекенд, щоб ніхто не змінював дані: docker compose stop backend.
  2. Візьміть останню копію з сервера або зі сховища (rclone copy offsite:readmania-backups/<файл> .).
  3. Відновіть базу: 
    docker exec -i readmania-db pg_restore -U readmania -d readmania \
  --clean --if-exists --no-owner < readmania-2026-11-15.dump
  4. Запустіть бекенд: docker compose start backend, перевірте /actuator/health і вхід на сайт.

Якщо сервер втрачено повністю: створіть нову ВМ за розділом 5, запустіть лише службу db, відновіть дамп, потім запустіть решту. За наявності готової інструкції це займає близько години, що вкладається у 3 години за ТЗ.

8Оновлення версії

  1. Зробіть позапланову резервну копію: /opt/readmania/backup.sh.
  2. Отримайте нову версію коду (git pull або архів від розробників).
  3. Перезберіть і перезапустіть контейнери: 
    docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
  4. Бекенд сам застосує нові міграції БД під час запуску. Перевірте журнал: docker compose logs backend | grep -i flyway.
  5. Перевірте вхід, каталог і оформлення тестового замовлення.
Відкат

Міграції змінюють схему БД, тому для повернення до попередньої версії відновіть резервну копію, зроблену перед оновленням, і запустіть попередню версію коду.

9Моніторинг і журнали

  • Стан: https://shop.example.com/actuator/health повертає {"status":"UP"}. Додайте цю адресу до зовнішнього моніторингу (UptimeRobot, Better Stack) з перевіркою кожні 5 хвилин і сповіщенням на пошту.
  • Контейнери: docker compose ps показує стан і healthcheck кожної служби; restart: unless-stopped перезапускає їх після збою чи перезавантаження сервера.
  • Журнали: docker compose logs -f backend (помилки, надсилання листів, міграції), docker compose logs frontend (запити nginx).
  • Диск: слідкуйте за вільним місцем (df -h); копії й журнали Docker з часом ростуть.
  • Оновлення безпеки ОС: sudo apt update && sudo apt upgrade раз на місяць або unattended-upgrades.

Безпека

  • Паролі користувачів зберігаються лише у вигляді хешів; сеанс — у cookie з HttpOnly, SameSite=Lax і Secure; є захист від CSRF.
  • Після 5 невдалих спроб входу вхід для email блокується на 15 хвилин; сеанс завершується через 30 хвилин бездіяльності.
  • Доступ до сервера — лише SSH за ключем; база даних і бекенд не мають відкритих портів.

Не змінюйте дані вручну

Залишки, бали й статуси пов’язані між собою. Виправлення SQL-запитами в обхід застосунку може порушити цілісність. Усі щоденні дії виконуються через вебпанель Менеджера.

11Типові проблеми

ОзнакаПричина й рішення
Бекенд не стартує, у журналі Connection refused до БДБаза ще запускається або неправильні DB_URL / пароль. Перевірте docker compose ps і змінні.
У журналі Validate failed: Migrations have failed validation / checksum mismatchЗастосовану міграцію змінили після запуску. Не редагуйте вручну; зверніться до розробників за новою міграцією або виправленням.
Після входу одразу «Сеанс завершено»Сайт відкрито через HTTP, а cookie має позначку Secure. Відкривайте лише через HTTPS і перевірте, що проксі передає X-Forwarded-Proto.
Листи не надходятьПеревірте SPRING_MAIL_* і журнал бекенду; переконайтеся, що провайдер не блокує порт 587; налаштуйте SPF/DKIM.
