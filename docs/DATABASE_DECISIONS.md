# Архітектурні рішення щодо бази даних (Database Architectural Decisions)

Цей документ фіксує узгоджені архітектурні рішення та рекомендації щодо проєктування реляційної схеми бази даних (PostgreSQL 17) для книжкового інтернет-магазину **ReadMania** на основі аналізу ТЗ, Специфікації вимог (SRS Лаба 2), сценаріїв UX (Лаба 3) та технічних стандартів розробки.

---

## 1. Реєстр архітектурних рішень

| № | Питання / Вимога | Прийняте рішення та реалізація | Обґрунтування та наслідки |
|---|---|---|---|
| **1** | **Видалення книги (M1)** | Реалізовано **м'яке видалення** (`deleted_at TIMESTAMPTZ NULL`). У таблиці `books` додано частковий унікальний індекс `uk_books_isbn_active` за умови `deleted_at IS NULL`. | Зберігає історію оцінок, замовлень та аналітику затребуваності. `order_items` зберігає незмінний знімок назви та ціни на момент замовлення. Жанр із видаленими (архівованими) книгами захищений правилом `ON DELETE RESTRICT`. |
| **2** | **Автори та нормалізація (3НФ)** | Створено окрему таблицю `authors` та проміжну таблицю зв'язку `book_authors` (M:N). Додано індекс за `LOWER(authors.name)` та FK-індекси. | Повна відповідність 3-й нормальній формі (3НФ) згідно з ТЗ та підтримка співіснування кількох авторів книги (SRS). Для імпорту/експорту з CSV як роздільник авторів затверджено символ `;`. |
| **3** | **Зберігання обкладинок (Backup & PaaS)** | Створено окрему таблицю `book_covers` зі стовпцем `data BYTEA` та `content_type VARCHAR(100)` (PK `book_id REFERENCES books(id) ON DELETE CASCADE`). | Дисковий простір PaaS-хостингів є тимчасовим (ephemeral), а резервне копіювання за ТЗ виконується через `pg_dump`. Зберігання в окремій таблиці виключає завантаження важких BLOB-даних під час вибірок каталогів та списків книг. |
| **4** | **Бонусні бали та паралелізм (C7, C8)** | Комбінована схема: журнал транзакцій `bonus_transactions` плюс денормалізований баланс `users.bonus_balance` з обмеженням `CHECK (bonus_balance >= 0)`. | Тільки підсумовування журналу транзакцій не захищає від подвійного списання (race condition) при конкурентних паралельних запитах. Стовпець із CHECK-обмеженням у поєднанні з блокуваннями транзакцій гарантує надійність на рівні СУБД. |
| **5** | **Прогрес читацьких викликів (C7, M4)** | Прогрес викликів не зберігається статично, а **обчислюється динамічно** SQL-запитом: враховуються замовлення користувача зі статусом `DELIVERED`, створені у проміжку між `challenges.created_at` та `challenges.deadline`; дарунки (`GIFT`) враховуються; рахується кількість придбаних примірників (`order_items.quantity`). | Забезпечує автоматичний перерахунок прогресу при коригуванні умов виклику менеджером. Фіксація завершення виклику записується в `challenge_completions`. |
| **6** | **Анонімізація контактів при видаленні неактивних акаунтів (M5)** | При видаленні користувача `orders.user_id` встановлюється в `NULL` (`ON DELETE SET NULL`), а сервісний шар M5 очищає персональні дані в замовленні (`recipient_name = NULL`, `recipient_phone = NULL`, `delivery_address = NULL`). | Забезпечує дотримання Закону України «Про захист персональних даних» та вимоги SRS п. 6 щодо збереження фінансово-бухгалтерської звітності без прив'язки до фізичної особи. |
| **7** | **Спосіб доставки для замовлення в дар (C10)** | Для благодійних замовлень типу `type = 'GIFT'` поле `delivery_method` залишається `NULL`. Обов'язковим є заповнення `institution_name` (перевіряється обмеженням `chk_orders_gift_institution`). | SRS не регламентує вибір кур'єрської служби покупцем для благодійних закладів; доставка здійснюється за узгодженим регламентом магазину. |
| **8** | **Захист від brute-force та токени відновлення (G3)** | Додано стовпці `failed_login_attempts INT NOT NULL DEFAULT 0` та `locked_until TIMESTAMPTZ` до `users`; створено окрему таблицю `password_reset_tokens` з унікальним токеном та строком дії 1 година. | Дозволяє блокувати обліковий запис на 15 хвилин після 5 невдалих спроб входу поспіль безпосередньо на рівні даних або комбіновано з кешем, а також забезпечує безпечне одноразове відновлення пароля. |
| **9** | **Запити на розблокування акаунтів (M6, M7)** | Створено окрему таблицю `unblock_requests` (з полями `user_id`, `reason`, `status IN ('PENDING', 'APPROVED', 'REJECTED')`, `resolved_by_user_id`, `manager_comment`). | Забезпечує прозорий життєвий цикл розгляду звернень заблокованих користувачів менеджером із можливістю надання текстового обґрунтування. |
| **10** | **Типи благодійних закладів (M8, M12)** | Додано стовпець `type VARCHAR(50) NOT NULL` з обмеженням `CHECK (type IN ('ORPHANAGE', 'BOARDING_SCHOOL', 'LIBRARY'))` та індексом. | Підтримує швидку фільтрацію закладів за категоріями (дитячий будинок, інтернат, бібліотека) у каталозі дарунків та панелі менеджера. |
| **11** | **Вибірки замовлень та безпечне архівування (M3, 7.2.2.6, 7.2.2.7)** | Додано часткові індекси `idx_orders_unpaid_awaiting` та `idx_orders_archived`; змінено зв'язок `gift_log.order_id` на `ON DELETE SET NULL`. | Забезпечує миттєву фільтрацію неоплачених замовлень (> 7 днів) та архівних замовлень (> 3 роки), а також дозволяє повністю видаляти застарілі замовлення зі збереженням оцінок `ratings` та звітного журналу `gift_log`. |
| **12** | **Фінансові формули та ліміти знижок як CHECK-обмеження** | Формули знижки (`discount_amount = points_used * 10`), суми до сплати (`total_to_pay = items_total - discount_amount`) та ліміту 30% (`discount_amount * 10 <= items_total * 3`) зафіксовані безпосередньо в DDL `orders`. | СУБД виступає останньою лінією оборони (Defense in Depth), унеможливлюючи запис некоректних розрахунків навіть при потенційних помилках у бізнес-коді. |
| **13** | **100% покриття FK індексами (Стандарт D7)** | На кожне поле зовнішнього ключа (`*_id`) створено окремий B-Tree індекс. Наявність перевіряється системним запитом у `SchemaIT`. | Усуває повне сканування таблиць при каскадних операціях та `JOIN`, що критично для високонавантажених операцій над замовленнями та каталогом. |
| **14** | **Сувора валідація схеми Hibernate (`ddl-auto: validate`)** | Усі JPA-сутності на 100% синхронізовані за типами з PostgreSQL 17 (`Instant` ↔ `TIMESTAMPTZ`, `BigDecimal` ↔ `NUMERIC(12,2)`, `Short` ↔ `SMALLINT`, `String` ↔ `VARCHAR/TEXT`, `byte[]` ↔ `BYTEA`). | Гарантує виявлення будь-яких невідповідностей типів або найменувань колонок на етапі запуску контексту застосунку та прогону CI/CD тестів. |

## 2. Уточнення та виправлення неточностей Специфікації вимог (SRS)

1. **Вимога M1 (Додавання/редагування видання):**  
   У переліку полів у тексті SRS було пропущено ISBN, хоча правила валідації та контролю унікальності явно спираються на ISBN. У таблиці `books` поле `isbn VARCHAR(20) NOT NULL` є обов'язковим з частковим унікальним індексом.
2. **Вимоги C10 та M8 (Благодійні замовлення та довідник закладів):**  
   У розділі 6 SRS посилання «C6» та «A5» виправлено на відповідні дійсні ідентифікатори вимог: **C10** (Замовлення в дар закладам) та **M8** (Керування закладами-одержувачами).

## 3. Загальні технічні стандарти реалізації міграцій (D7)

- **Первинні ключі:** `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`. `orders.id` виступає єдиним унікальним номером замовлення.
- **Фінансові дані:** `NUMERIC(12,2) NOT NULL CHECK (... >= 0)`.
- **Часові мітки:** `TIMESTAMPTZ` (відповідає `java.time.Instant` у Hibernate).
- **Індексація FK:** Згідно з вимогою D7, кожне поле зовнішнього ключа покрито індексом (автоматично валідується тестом `SchemaIT`).
- **Оптимістичне блокування:** Стовпець `version BIGINT NOT NULL DEFAULT 0` у таблицях `orders` та `books` для запобігання втраті оновлень (Lost Updates).
- **Обмеження знижок:** Знижка розраховується за формулою `discount_amount = points_used * 10` та не перевищує 30% вартості замовлення (`discount_amount * 10 <= items_total * 3`).
